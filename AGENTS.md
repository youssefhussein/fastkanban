# Repository Guidelines

## Project Structure & Module Organization
This is a Next.js 16 + Convex app using the App Router.
- `app/`: routes and page-level UI (`app/page.tsx`, `app/signin/page.tsx`, `app/server/page.tsx`).
- `components/`: shared React components and providers (for example `ConvexClientProvider.tsx`).
- `convex/`: backend schema, queries, mutations, auth config, and generated API types.
- `lib/`: shared utilities (`lib/utils.ts`).
- `public/`: static assets and icons.

Do not hand-edit files under `convex/_generated/`; they are generated by Convex.

## Build, Test, and Development Commands
DO NOT RUN `pnpm dev` unless told to, I already have the server running
Use `pnpm` (lockfile is `pnpm-lock.yaml`).
- `pnpm install`: install dependencies.
- `pnpm lint`: run ESLint across the repo (required before PRs).
- `pnpm build && pnpm start`: production build and local production server.

## Coding Style & Naming Conventions
- Language: TypeScript with `strict` mode enabled (`tsconfig.json`).
- Indentation: 2 spaces; prefer consistent semicolon and quote usage per existing files.
- React components: `PascalCase` names and files; utility/functions: `camelCase`.
- App routes: lowercase folder names under `app/`.
- Convex: keep validators explicit and avoid unsafe casts.
- Avoid `any` and `unknown` in application code.
- Avoid `useEffect()` as much as possible.

Linting uses Next.js core-web-vitals + TypeScript + Convex recommended configs (found in .cursor/rules/convex_rules.mdc ). Prettier is present with default config.

## Testing Guidelines
There is no dedicated test suite yet. Current quality gate is:
1. `pnpm lint` must pass with zero errors.
2. Manually verify core flows: sign-in/out, home page data fetch, and Convex mutations.

When adding tests, place them near the feature (`*.test.ts` / `*.test.tsx`) and focus on behavior, not implementation details.

## Commit & Pull Request Guidelines
History is currently minimal and uses short, imperative commit subjects (example: `init and setup shadcnui`).
- Keep commit titles concise, action-oriented, and scoped to one change.
- PRs should include: summary, impacted paths, setup/env changes, and screenshots for UI changes.
- Link related issues/tasks and list validation steps you ran (at minimum `pnpm lint`).
